## 一、方案总览

```
┌────────────────────── 服务端(181, FastAPI :2334) ──────────────────────┐
│  admin UI(static/admin/index.html)                                      │
│    │ /api/admin/push-agent（选设备→选配置包/版本→推送）                   │
│    ▼                                                                     │
│  agent_repo.py(新增) ── agent_configs / agent_versions / deploy_status  │
│    │ 按 {agent_name, rev} 取配置包 → 打包(agent内容+resources+skills等)   │
│    ▼                                                                     │
│  dispatch.py ── WS type="dispatch_agent"（载荷含 metadata/version/sha256）│
│    ├─ 在线: 直发  │  offline_queue 补发                                   │
└──────────────────────────────────────────────────────────────────────────┘
                                │ WebSocket
┌────────────────────────────── 员工机 sidecar ───────────────────────────┐
│ sidecar.py 收到 → dispatch.py DispatchExecutor                           │
│   ① verify sha256(包)   ② 无此 agent → POST /v1/admin/agents(create)      │
│                        ③ 已有 → version/rev 比对 → PUT /v1/admin/agents/id │
│   ④ attachments/skills/mcp 按需分通道下发（复用 dispatch_skills 通道）       │
│   ⑤ mark_managed('agent', id) + deploy_status 本地记录                     │
│   └─ dispatch_result 回执（含 agent_id / deployed_rev / error）            │
└──────────────────────────────────────────────────────────────────────────┘
```

**核心权衡（已按任务背景定稿）：**
- **升级用 `PUT` 全量更新（≠ delete+create）**：保住 agent_id 与员工会话/历史，避免删建导致 Fork 侧会话丢失与受管标记错乱。
- **版本双轨**：`version`（语义化，包内 `metadata.version`）+ `rev`（服务端自增单调版本号）。设备侧"已部署版本"以 `rev` 为准作为对账锚点。
- **内容指纹**：`sha256` = 对 `agent` 配置规范序列化（sort_keys + ensure_ascii=False）并把 `resources`/`skills` 全部内容按路径/名称字典序拼接参与整体哈希；任何字段/资源变化都会产生新哈希。
- **鉴权**：admin API 复用现有 `X-Admin-Token`（`require_admin`）；设备推送走已有 WS + 每设备 `managed_key` 绑定鉴权，无新增鉴权面。

## 二、Agent 配置包规范（字段级）

### 2.1 包结构定义（标准 JSON，顶层为 agent_config 对象）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `metadata` | obj | ✅ | 包元数据（见 2.2） |
| `agent` | obj | ✅ | CreateAgentCommand 的主体（见 2.3），字段名对齐受管 API schema |
| `resources` | obj: map\<string,string\> | ❌ | Agent 关联文件：`{相对路径: 文件内容}`，对应 GET /v1/admin/agents/{id}/files 的关联文件（如知识库/工作目录模板） |
| `skills` | obj[] | ❌ | 关联 Skill 配置清单（见 2.4），每个元素是独立 skill 包，等同 dispatch_skills 通道的 skills 元素 |
| `mcp` | obj[] | ❌ | 关联 MCP Server 配置清单（见 2.5） |
| `providers` | obj[] | ❌ | 关联模型 Provider 配置（batchUpsert 入参），默认模型引用这里声明的 provider |
| `attachments` | obj[] | ❌ | Agent 关联附件（/v1/admin/agents/{id}/files 语义），元素 `{name, path, content(b64)}`，推送后落 agent 目录 |

### 2.2 `metadata` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | ✅ | Agent 唯一名（与 `agent.name` 一致），作为包的跨版本稳定主键 |
| `version` | string | ✅ | 语义化版本，如 `1.2.0`，支持 `-rc.1` 后缀（管理员显式声明） |
| `rev` | int | ✅ | 服务端版本自增号（创建时分配，同一 Agent 内单调递增） |
| `description` | string | ❌ | 包描述 |
| `author` | string | ❌ | 维护者 |
| `created_at` | string | ✅ | ISO8601 UTC |
| `sha256` | string | ✅ | 内容指纹（见 2.6），推送时校验 |
| `build_info` | obj | ❌ | `{platform, cherry_version, fork_version}` 兼容性留痕 |

### 2.3 `agent`（CreateAgentCommand 映射）

对齐受管版实测 `CreateAgentCommand` schema（name/type/model/instructions/configuration/tools/skills）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | ✅ | 唯一名（= 包 key），定稿后不可变更 |
| `type` | string | ✅ | 如 `claude-code`（对齐 sidecar cmd_deploy 默认） |
| `model` | string | ✅ | 默认模型 id（如 deepseek/deepseek-v4-flash），须存在于受管 providers |
| `instructions` | string | ✅ | 系统提示词 |
| `configuration` | obj | ✅ | `{permission_mode, max_turns, env_vars, ...}` 透传；不与 `agent`/`metadata` 嵌套，保持 schema 对齐 |
| `tools` | string[] | ❌ | 启用工具列表（name 或 uri 语义，可空则省略） |
| `skills` | string[] | ❌ | 引用本包顶层 `skills[]` 的 id |
| `description` | string | ❌ | 可读描述 |

> 兼容：下发 `agent` 时只传受管版接受的字段；员工机 Fork 版本过低导致未知字段被拒时，方案按风险 R3 降级处理。

### 2.4 `skills` 条目

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✅ | skill 唯一 id（与 `agent.skills[]` 引用一致） |
| `name` | string | ✅ | 名称 |
| `version` | string | ❌ | skill 版本（落盘 skills_dir/{id}.json 的 version 字段） |
| `content` | string | ❌ | skill 正文（内联） |
| `package_url` | string | ❌ | 与 `content` 二选一：内联正文 或 外链包 |
| `metadata` | obj | ❌ | 透传（权限模型等） |

### 2.5 `mcp` 条目

受管版提供 `GET/POST /v1/admin/mcp`、`/v1/admin/mcp/{id}`，推荐字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | ✅ | MCP 名 |
| `type` | string | ✅ | `stdio` / `sse` / `http` |
| `url` | string | 按 type | `sse`/`http` 必填；`stdio` 可无 |
| `command` | string | 条件 | `stdio` 用（如 npx 服务启动命令） |
| `args` | string[] | ❌ | stdio 参数 |
| `env` | obj | ❌ | 环境变量占位（敏感值不落包，用 `${SECRET:变量名}` 占位，由部署侧注入） |
| `enabled` | bool | ❌ | 默认 true |

> 服务端只做引用下发（注册/落盘），不做二进制分发；MCP 二进制由 `command` 在端上按需拉取。

### 2.6 哈希校验（recipe）

```
sha256(agent_config) = sha256(
    b"name=" + agent.name +
    b"|rev=" + str(metadata.rev) +
    b"|" + canonical_json(config.agent) +        # 按 key 排序序列化
    b"|resources:" + 各路径→内容按路径字典序拼接 +
    b"|skills:" + 各 skill id+content 按 id 字典序
)
```
- 服务端创建版本时计算并存 `agent_versions.sha256`；推送请求携带。
- Sidecar 收到先 `verify_sha256(pkg)` 再执行；不过校验 → `dispatch_result(success=false, error="hash_mismatch")`，且不落盘、不调 API。
- `rev` 参与哈希：同内容不同 rev 哈希不同，保证"升级必改哈希"。

## 三、版本管理模型（服务端）

### 3.1 数据表设计（server/db.py 新增 3 表）

```sql
-- 1) Agent 配置最新态（按 name 主键）
CREATE TABLE IF NOT EXISTS agent_configs (
    name        TEXT PRIMARY KEY,          -- Agent 唯一名（包 key）
    latest_rev  INTEGER,                   -- 当前最新 rev
    latest_sha  TEXT,                      -- 最新包 sha256
    updated_at  TEXT,
    locked      INTEGER DEFAULT 0          -- 1=锁定禁发布（灰度/维护期）
);

-- 2) 版本历史（一 Agent 多版本）
CREATE TABLE IF NOT EXISTS agent_versions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    name       TEXT NOT NULL,              -- 包名（外键语义）
    rev        INTEGER NOT NULL,           -- 该 Agent 内自增
    version    TEXT NOT NULL,              -- 语义化版本
    config     TEXT NOT NULL,              -- 完整包 JSON（agent/resources/skills/mcp/providers/attachments）
    sha256     TEXT NOT NULL,
    created_by TEXT,
    created_at TEXT,
    build_info TEXT,
    UNIQUE(name, rev)
);

-- 3) 设备级部署状态（对账锚点）
CREATE TABLE IF NOT EXISTS deploy_status (
    device_id     TEXT NOT NULL,
    agent_name    TEXT NOT NULL,
    rev           INTEGER NOT NULL,        -- 设备端已部署 rev
    version       TEXT,                     -- 语义化版本（冗余展示）
    sha256        TEXT,                     -- 设备端实际哈希
    updated_at    TEXT,
    PRIMARY KEY (device_id, agent_name)
);
```

> 迁移：在 `init_db()` 中追加 `CREATE TABLE IF NOT EXISTS` + 幂等迁移辅助（对齐现有 `_migrate_devices_managed_key` 模式）。

### 3.2 版本模型

- **`rev` 自增**：`INSERT` 时 `rev = (SELECT COALESCE(MAX(rev),0)+1 FROM agent_versions WHERE name=?)`，作为服务端唯一真实增量锚点。
- **`version` 语义化**：管理员显式控制（1.2.0 / 1.2.0-rc.1），用于 UI 展示与灰度门槛，不独立做主版本。
- **保留策略**：全量保留（SQLite 体积可接受）；后续膨胀再做 `prune(keep_last N)`，本期不做。

### 3.3 升级流程（rev+1 → 推送）

1. 管理员在后台上传/编辑包 → 服务端校验（字段类型、skills/mcp 引用在包内存在、json schema）→ 写 `agent_versions`（rev+1、version、sha256）→ 更新 `agent_configs.latest_rev/latest_sha`。
2. push 时按 `agent_versions` 取目标包，经 WS `dispatch_agent(action=update, agent=<agent 内容>, metadata=..., resources=..., skills=...)` 下发。
3. 员工侧 sidecar `_handle_dispatch_agent(action=update)` → 校验 sha256 → `cherry.put_agent(agent_id, agent包)` → 更新本地 deploy 状态（managed_entity 已存在则仅更新版本记录）。
4. 服务端 `deploy_status` 记录 `rev/version/sha256` → 对账锚点（3.5）。

### 3.4 回滚方案

| 项 | 说明 |
|---|---|
| 管理入口 | `POST /api/admin/push/agents` 支持 `target_rev`（可传历史 rev；也可按 version 定位） |
| 流程 | 服务端从 `agent_versions` 取目标 rev 完整包 → sha256 校验 → 下发 `action=update`（sidecar `put_agent` 幂等覆盖）→ deploy_status 更新为回滚 rev |
| 副作用 | 回滚只覆盖 `agent` 主体，**不自动回滚** skills/mcp/providers 依赖（各自独立版本通道），UI 需显式提示 |

### 3.5 对账一致（reconcile 增强）

- sidecar 回执 `dispatch_result` 增加 `deployed_rev / deployed_sha` 字段；服务端 `_on_dispatch_result` 落 `deploy_status`。
- `reconcile_summary` 增加 `expected_agent_configs`（按设备给期望最新 rev）与 `device_deploy`（当前 deploy_status）两节。
- sidecar 对账：期望 rev ≠ 本地已部署 rev → 标 modified → 触发重推（`update` 动作）；本地受管但服务端不再期望 → `managed_extra`（不自动删，留后台确认）。
- 向后兼容：无 deploy_status 记录的存量设备退化为内容比对（双轨对账）。

### 3.6 灰度推送（Pilot → 分批）

> 本期**设计预留、UI 后置**（回滚/API 先行）：推荐按 `devices.group` 分组分批，不引入灰度新组件。

| 项 | 说明 |
|---|---|
| 灰度策略 | 复用 `devices.group`（default / pilot 等）；推送目标支持 `group` 或 `devices` 列表 |
| 推进规则 | 先 pilot 小组推送 → 全 success + 人工确认 → 再推目标组 |
| 失败取消 | 任一分批有 fail → 标记该组部署失败，自动回滚为目标 rev 之前一个 rev（rev-1）下发 |
| 锁定保护 | `agent_configs.locked`=1 时 push 请求返回 400（回滚中/维护期禁推） |

## 四、服务端 API 设计（新增）

### 4.1 统一约定

- 鉴权：全部加 `dependencies=[Depends(require_admin)]`（沿用 `X-Admin-Token`，复用现有 `admin_auth`）。
- 分页：沿用 `_pagination(limit, offset)`（默认 100、上限 500）。
- 响应统一：`{"ok": bool, "data": ..., "error": str|null}`；错误语义走 HTTP 状态码 + detail。

### 4.2 端点清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET  | `/api/admin/agent-configs` | 配置包列表（name/rev/version/updated_at/locked） |

| GET  | `/api/admin/agent-configs/{name}` | 包详情（含最新包内容） |

| POST | `/api/admin/push/agents` | **推送/升级/灰度主端点**（见 4.3） |
| GET  | `/api/admin/push/jobs` | 推送任务列表/单任务详情（含每设备回执状态） |

## 六、修复方案（已知 BUG —— 派发链路断链）

### 6.1 问题确认（实读代码）

| # | 症状 | 根因 |
|---|---|---|
| 1 | 40 号机 `/v1/agents` 返回 404 | `sidecar/lib/cherry_client.py` 的 `list_agents/create_agent/patch_agent/put_agent/delete_agent` 全部走官方通用 `/v1/agents*`；受管版无官方路由，有效路由是 `/v1/admin/agents*` |
| 2 | 40 号机 `/v1/admin/*` 返回 Forbidden | 受管鉴权 key 没对上：sidecar 默认 `CherryClient(api_key="")`，`_request` 在 api_key 为空时不发任何鉴权头；即便有值，也同时发 `Authorization: Bearer` 与 `x-api-key` 双侧，受管版只认 Bearer（且需匹配受管版内部配置的 managed_key） |

### 6.2 修复方案

**A. `sidecar/lib/cherry_client.py`：加受管模式（路径前缀 + 单一 Bearer 头）**

```python
class CherryClient:
    def __init__(self, host="127.0.0.1", port=23333, api_key="",
                 timeout=10.0, managed: bool = True):
        self.host, self.port, self.api_key, self.timeout = host, port, api_key, timeout
        self.managed = managed          # 受管版（默认 True，对齐当前部署形态）
        self.base_url = f"http://{host}:{port}"
        self._admin = "/v1/admin"       # 受管端点前缀

    def _path(self, p: str) -> str:
        """受管模式把 /v1/xxx 映射为 /v1/admin/xxx。"""
        return (self._admin + p if p.startswith("/v1/") else p) if self.managed else p

    def _request(self, method: str, path: str, data: Optional[dict] = None):
        headers = {}
        if self.api_key:
            headers["Authorization"] = f"Bearer {self.api_key}"   # 只发 Bearer，去掉 x-api-key
        # 受管模式强制要求 key —— 缺失时告警，避免静默 401/403
        if self.managed and not self.api_key:
            logger.warning("受管模式缺 managed_key（api_key 为空）, /v1/admin/* 将 401/403")
        url = self.base_url + self._path(path)
        ...（其余与现状一致，去掉 x-api-key 头）
```

同步把 `create_agent/patch_agent/put_agent/delete_agent/list_agents` 的路径改写为 `/v1/admin/agents`、`/v1/admin/agents/{id}`；新增 `list_skills/create_skill`（`/v1/admin/skills`）、`list_mcp/put_mcp`（`/v1/admin/mcp`、`/v1/admin/mcp/{id}`）供 skills/mcp 通道使用（仍走本类统一下发）。

**B) `sidecar/sidecar.py`：受管 key 注入 CherryClient**

```python
# 构造处（保留 fork 用 key 同步到 cherry）：
self.cherry = CherryClient(host=fork_cfg.get("host", "127.0.0.1"),
                           port=fork_cfg.get("port", 23333),
                           api_key=fork_cfg.get("api_key", ""),   # 受管管理 key，非员工 api_key
                           managed=True)
# _ensure_managed_key() 拉到受管 key 后，同时同步两处：
#   self.fork.api_key = key
#   self.cherry.api_key = key
```

> **关键语义**：这里的 `api_key` 是「受管版 /v1/admin/* 的受管管理 key」（Fork 侧 `feature.api_gateway.managed_key` 语义），**不是** 设备级 managed_key（后者仅用于 WS 绑定鉴权，JJC-20260818-001）。两把 key 职责分离，不要混用。

**C) 40 号机 Forbidden 根因核查（受管版侧）**

- 受管版的 `/v1/admin/*` 用 `feature.api_gateway.managed_key`（或等同配置）做 Bearer 比对；sidecar 必须使用同串。落地第 4 步时在 40 号机：
  1. 读受管版配置确认 managed_key 来源（config 文件/环境变量）；
  2. `curl -H "Authorization: Bearer <受管key>" http://<40机>23333/v1/admin/agents` 直测 200；
  3. 已有 `GET /v1/admin/managed-key` 回环端点（`_fetch_managed_key` 在用）返回的 key 与手测 key 一致，则 sidecar 无需额外配置，`_ensure_managed_key` 同步给 cherry 即可。

|---|---|
| `/v1/admin/*` 不再 404/403 | 修复后 `curl -H "Authorization: Bearer <key>" http://<40号机>:23333/v1/admin/agents` 返回 200 正常 list |

> **审计补充（P1 前置约定，2026-08-19 审计官审核后固化）**
> `action=update` 对 agent 配置体必须**无条件走 `put_agent`（PUT 全量覆盖）**，不得沿用现有 `dispatch.py` 中「有 package_url 走 put_agent，否则走 patch_agent」的启发式分流。
> 原因：patch（PATCH 部分更新）不会清除被删除的字段（如从 tools 移除某工具），会造成「升级不删配置」BUG。
> PATCH 仅保留给单字段热修（本期可移除）；`rev+1` 的正式升级一律 PUT。在步骤4改造 `_handle_dispatch_agent` 时落地此约定。
