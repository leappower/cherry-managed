## 〇、本版与 v1.0 的差异（为什么重做）

v1.0 之后我错误地把「方案 A」做成了**只覆盖 Sidecar 层**的片面方案，把 Fork 层（UI 锁死 + 模型管控 R1）排除在外，还声称「R1 需单独方案」。这导致方案残缺、割裂。

**v2.0 纠正**：一份完整方案，**两层架构（Fork + Sidecar）+ 服务端**全部包含，R1-R7 每条需求都有明确实现路径，不再有「需单独方案」的悬空项。

## 一、目标（一句话）

给公司内部做「CherryStudio 企业受管版」：**公司统一派发模型/Agent/SKILLS/MCP，员工端这些受管项锁死不能改，但员工仍可自配自己的模型；公司模型 Key 不泄露；数据回采驱动 Agent 进化；员工自己升级不破坏受管状态。**

### 三层职责分工（关键，不再割裂）

| 层 | 改本体? | 职责 | 覆盖需求 |
|----|--------|------|---------|
| **服务端 server/** | 否 | 统一管理所有设备、派发调度、数据仓库、更新服务 | 全局中枢 |
| **Fork 层 fork-patches/** | **是** | 锁死 UI、隐藏 Key、禁用更新、受管标记 | R2/R5/R7 |
| **Sidecar 层 sidecar/** | 否 | 远程派发 Agent/SKILLS、数据采集、完整性校验、自愈 | R1/R3/R4/R6 |

> **核心认知**：Fork 层解决「员工不能乱改」，Sidecar 层解决「远程管一切」，服务端是「统一调度中枢」。**三者配合才是完整受控分发系统，缺一不可。**

## 四、Fork 层（改 CherryStudio 本体）→ 锁死 + 受管

| 改动点 | 内容 | 作用 | 需求 |
|--------|------|------|------|
| ① UI 锁死 | 设置页 provider/model/mcp/skills/agent 受管项只读/隐藏 | 员工不能乱改 | R5 |
| ② UI 锁死 | 隐藏公司模型 API Key 显示 | 防员工拿走 key | R2 |
| ③ 入口接管 | 禁用原生更新按钮 | 防官方升级覆盖 | R7 |
| ④ 配置注入 | `feature.api_gateway.host=127.0.0.1` 固定 | 只允许本地 Sidecar 访问 | 安全 |
| ⑤ 受管开关 | `config.json` 加「受管标记」，UI 检测即锁死 | 一个版本两种模式 | R5 |

**源码级依据**（已求证）：
- 设置页是普通 React 页（`src/renderer/routes/settings/provider.tsx`、`model.tsx`），**无 managed/policy/readonly 机制**，彻底锁死 UI 只能 Fork 改代码
- UI 锁死改动仅在 renderer 层路由/组件，**比改主进程轻**
- 一个版本可同时支持受管/非受管（config.json 标记切换）

## 五、Sidecar 层（不改本体）→ 实时控制 + 数据闭环

| 能力 | 作用 | 需求 |
|------|------|------|
| ① 服务端对接 | 主动 WS 连服务端（绕开端口转发） | 全局 |
| ② Agent/SKILLS 派发+回收 | 经本地 127.0.0.1:23333 调 API | R3/R4 |
| ③ 模型管控执行 | 经 Fork 层接口/直写数据目录，派发/收回 `企_` 模型 | R1 |
| ④ 完整性校验 | 校验 Fork 版文件哈希，被覆盖→报警/重打/上报 | R7 |
| ⑤ 数据采集 | 会话摘要、使用频次、报错 → 上报服务端 | R6 |
| ⑥ 开机自启+自愈 | 掉线重连、崩溃自启 | 全局 |

**Sidecar 常驻职责**：
1. 开机自启，连接服务端 WS
2. 收到派发指令 → 调 `cherry_client` 执行（创建/更新/回收 Agent）
3. 收到模型管控指令 → 经 Fork 层接口执行（派发/收回 `企_` 模型）
4. 收到 SKILLS 同步指令 → 写本地数据目录
5. 定时上报状态 + 使用数据（按需采集）
6. 断线自动重连

```json
  "os": "windows",

  "token": "***"
```

### 7.2 派发 Agent（服务端 → Sidecar）
```json
{

  "action": "create",          // create | update | delete | disable
  "agent": {
    "name": "企_客服助手",
    "model": "deepseek:deepseek-v4-flash",
    "instructions": "...",

    "configuration": {"permission_mode": "bypassPermissions", "max_turns": 100}

  "skills": ["skill-a@v1.2", "skill-b@v2.0"],
  "request_id": "req-001"
}
```

### 7.3 派发模型（服务端 → Sidecar，R1 预留）
```json
{
  "type": "dispatch_provider",
  "action": "add",             // add | remove | update
  "provider": {
    "name": "企_DeepSeek",
    "type": "openai",
    "api_key": "***",          // 经 Fork 层接口注入，员工端不可见
```

## 八、核心流程

### 8.1 设备上线
```
1. Sidecar 开机自启
2. 连接服务端 WS
3. 发送 register（设备信息 + token）
4. 服务端登记设备 → 返回「该设备应有哪些 Agent/SKILLS/模型」清单
5. Sidecar 比对本地 → 差异同步（缺的创建，多的回收）
6. 进入常驻监听
```

### 8.2 派发新 Agent（管理员操作）
```
1. 管理员在服务端「派发 Agent 企_客服助手 给 设备组A」
2. 服务端向组内每台 Sidecar 发 dispatch_agent
3. Sidecar 调 cherry_client.create_agent() 创建
4. 回执 dispatch_result
5. 服务端更新设备状态
```

### 8.3 派发/收回模型（R1，管理员操作）
```
1. 管理员在服务端「派发 企_DeepSeek 给 设备组A」
2. 服务端发 dispatch_provider action=add
3. Sidecar 经 Fork 层接口注入 provider（员工端 UI 锁死不可见）
4. 回执
5. 收回：发 action=remove，Sidecar 移除企_ 前缀项
```

### 8.4 回收 Agent
```
1. 管理员「回收 企_客服助手」
2. 服务端发 dispatch_agent action=delete
3. Sidecar 调 delete_agent() 删除
4. 回执
```

### 8.5 数据采集闭环（R6）
```
1. Sidecar 按需采集使用数据 → 上报
2. 服务端存储 → 分析
3. 分析结果 → 驱动新 Agent/SKILLS 开发
4. 派发回设备
```

## 九、关键设计决策

### D1 企业模型命名隔离（R1）
- 企业派发模型统一加前缀 `企_`（如 `企_DeepSeek`）
- 员工自配模型自由命名，互不干扰
- 收回时从预设层移除 `企_` 前缀项

### D2 Key 保护双保险（R2）
- 强方案：公司模型走**模型网关**，员工端只看到网关 URL，Key 藏网关侧
- 兜底：UI 锁死隐藏 Key 显示

### D3 Agent 完整打包（R3）
```
agent-package/
├── agent.json            # Agent 定义
├── skills/               # SKILLS 目录
├── mcp/                  # MCP 配置
└── data/                 # 预设数据文件
```
- 服务端版本管理，Sidecar 按版本同步

### D4 SKILLS 版本仓库（R4）
- 复用 NAS 分发思路（SKILL经验蒸馏.md）系统化
- `skills-repo/{name}/{version}/`
- Sidecar 拉取指定版本 → 写员工端 `.claude/skills`

### D5 自进化双路径（R6）
- ① 预设 SKILLS（Agent 自带进化逻辑）
- ② 服务端数据闭环（采集→分析→开发新 Agent/SKILLS 回推）

### D6 设备鉴权
- 每台设备唯一 `device_id` + 简单 token（老板已定）
- 服务端 WS 连接需 token，防未授权设备连入

### D7 派发幂等性
- 每个指令带 `request_id`，Sidecar 执行后回执
- 服务端记录已派发状态，重复派发不重复创建
- 断线重连后，服务端重发未确认指令

### D8 设备分组
- 支持按组派发（如「设计组」「客服组」）
- 组内设备统一收指令

### D9 离线处理
- 设备离线时，指令进入队列
- 设备重连后，服务端补发积压指令

## 十、技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 服务端框架 | Python FastAPI + uvicorn | 轻量、异步 WS 支持好、与 Sidecar 同语言 |
| WS 库 | `websockets`（服务端）/ `websocket-client`（Sidecar） | 成熟稳定 |
| 数据存储 | SQLite（起步）→ PostgreSQL（规模化） | 起步简单，可扩展 |
| Sidecar 常驻 | Python + systemd（Linux）/ NSSM（Windows） | 开机自启、崩溃自愈 |
| 设备注册表 | 内存 + SQLite 持久化 | 在线状态实时，历史持久 |
