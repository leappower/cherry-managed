## 一、目标

为每台受管设备**自动生成唯一 managed_key**（非全局静态 token），并在设备注册时**上报绑定到服务器**（server 登记该 key 属哪台 device），实现设备级鉴权与服务器端可识别/核验。

## 二、现状核实（已实读 cherry-managed）

| 项 | 现状 | 缺口 |
|----|------|------|
| device_id | sidecar `_device_fingerprint()`（Windows MachineGuid+hostname hash）生成，存 user 级 device.json | ✅ 已有 |
| WS register | sidecar `_register()` 上报 device_id/device.json 字段 + **token**（`sidecar.json server.token` 静态 `CHANGE_ME_managed_token`） | ⛔ token 是**全局单一静态**，非每设备唯一自动生成 |
| 服务器鉴权 | `ws_server._authorize` 用 `self.token = config.get("token")` 对首条 register 做 timing-safe 比对 | ⛔ 全局单一 token，无法区分设备 |
| devices 表 | 有 `token` 字段（存 register 上报 token）+ device_id PK | 可承载 device-specific 的 managed_key |
| managed_key 概念 | 文档 F-3：`feature.api_gateway.managed_key` 用作 Fork `/v1/admin/*` bearer 管理 key | 未实际自动生成/绑定 |

## 三、方案（核心改造）

### A. Sidecar：managed_key 自动生成（首次运行）
1. 新增 `_managed_key()`：首次运行自动生成唯一 key
   - 源：`secrets.token_urlsafe(32)`（或 uuid4 + 机器指纹混合）
   - 落盘：用户级配置目录**新文件**（如 `{userData}/managed_key` 或并入 device.json），权限收紧
   - **幂等**：已存在则不重复生成，重启复用（对齐 device_id 的生成→落盘模式）
2. 生成时机：`first-run` 或首次 `_register` 前（与 device.json 同生命周期）
3. 敏感处理：与现有 token 一致，不落明文日志；Windows ACL / POSIX 0600 保护

### B. Sidecar → 服务器：绑定上报
1. `_register()` 上报新增字段 `managed_key`（与 device_id 同报）
2. register 首条消息鉴权：若用 managed_key，服务器按 device 校验（见 C）

### C. 服务器：绑定登记 + 设备级鉴权（关键）
1. **绑定登记**：`device_registry.register()` 增加 managed_key 落库（devices 表新增 `managed_key` 列，或复用 token 列语义升级）
2. **设备级鉴权**（改造现全局单一 token）：
   - register 上报 device_id + managed_key → 服务器查 devices[device_id].managed_key 比对（timing-safe）
   - 已登记设备：按 device 专属 key 校验（**新增能力**：不再是全局一把 token）
   - 首末/未登记设备：保留现有路径（首次可用注册 token 或申领流程）
3. 服务器端管理后台（可选）：Web UI 展示已绑定设备及其 managed_key（脱敏）

### D. 与 Fork managed_key（F-3）的关系（⚠️ 设计决策，见 CL1）
managed_key 是否同时作为 Fork `/v1/admin/*` 的 bearer 管理 key：
- **CL1-A（推荐）**：managed_key 仅作「设备↔服务器 WS 绑定凭据」；Fork 管理路由仍用现有独立 managed_key 配置（职责分离，安全）
- **CL1-B**：统一为同一把 key——设备 managed_key 也用于调 Fork /v1/admin/*（sidecar→fork），服务器转发光 key 或 fork 侧持同 key

## 四、关键决策（NEEDS CLARIFICATION）

| # | 决策点 | 建议 |
|---|--------|------|
| CL1 | **managed_key 语义**：仅 WS 绑定，还是同时作 Fork /v1/admin/* 管理 key？ | **CL1-A**（职责分离，仅 WS 绑定；Fork 管理 key 沿用 F-3 独立配置） |
