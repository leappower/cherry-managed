## 第 1 轮质询（技术可行性靶点）

### Q1 🔴 R1 模型管控通道未打通
- **方案假设**: R1 经"注入器接口注入"实现
- **源码事实**: v1.9.7 provider 存 redux `llm.providers`→localStorage(leveldb)；无 provider HTTP API、无 provider IPC
- **缺陷**: "注入器接口注入"未验证注入脚本能否访问 redux store / 直写 leveldb
- **调优**: M0 新增实测"渲染进程注入改 provider 可行性"；不可行则 R1 降级为模型网关（D2 强方案）

### Q2 🔴 锁死 UI 依赖 asar，Electron 41 未验证
- **方案假设**: 注入器改 asar 锁死 UI
- **源码事实**: v1.9.7 = Electron 41.2.1 + asar；fuses 可能阻止修改
- **缺陷**: asar 改不动则 R5/R1/R3 全崩，无备选
- **调优**: M0 实测 Electron 41 asar 可改性；不可改则用 preload 注入（sandbox:false+webSecurity:false 支持，不改 asar）

### Q3 🟡 Git Bash 依赖定义不清（6B.1）
- **方案假设**: 智能体依赖 Git Bash，缺则需远程装
- **源码事实**: 自带 bundled MinGit 兜底 git 命令；智能体（claude-code）需 bash 终端，MinGit 不保证 bash；v1.9.7 原生有 GitBashPath 管理
- **缺陷**: "需要装什么"不清；未利用原生机制
- **调优**: 明确检测完整 Git for Windows（bash.exe）；复用 GitBashPath

### Q4 🟡 补丁包技术栈未定
- **方案假设**: NSIS exe（Sidecar + 注入器 + 标记 + 卸载器）
- **缺陷**: Sidecar 是 Python，员工机无 Python；NSIS 跨平台构建未验证；注入器一次性 vs Sidecar 自愈反复重打耦合
- **调优**: Sidecar 用 PyInstaller 打包成独立 exe；NSIS 只做壳；M0 验证构建链路

### Q5 🔴 升级免疫（R7）与"锁定 v1.9.x"矛盾
- **方案假设**: 策略 A 放任升级 + 自愈重打
- **老板拍板**: 锁定 v1.9.x
- **矛盾**: 放任升级到 v2.0.1 会移除 agents API，Sidecar 派发全断；与锁定 v1.9.x 直接冲突
- **调优**: R7 改为"锁定 v1.9.x + 禁用官方更新通道"（config.json autoUpdate:false + 可选 feedURL 指向内网），比自愈简单可靠。需老板重拍板

### Q6 🟡 SKILLS 派发通道未打通（R4）
- **方案假设**: Sidecar 写 `.claude/skills`
- **源码事实**: SKILLS 走 IPC `Skill_*` + agents.db skills 表（content_hash 版本管理）
- **缺陷**: 非简单写目录，需 IPC 注入或直写 agents.db
- **调优**: 明确 SKILLS 写入通道（IPC `Skill_*` 优先 / 直写 agents.db）；给 SKILLS 数据模型

## 第 2 轮质询（数据模型 + 部署 + 安全 + 运维靶点）

### Q7 🔴 受管标记（managed）没有存储载体
- **方案假设**: D13/D15 派发时打 managed:true，注入器据此隐藏删除按钮
- **源码事实**: v1.9.7 agents 表无 managed 列；provider/SKILLS/MCP 同理无 managed 概念
- **缺陷**: managed 标记存在哪未定义；加列需迁移 agents.db（锁库风险）
- **调优**: 受管标记走**旁路 sqlite**（Sidecar 维护 managed_registry.db，记录 id→managed 映射），注入器经 preload 暴露的 IPC 读；Sidecar 唯一写者，不动 agents.db，无锁库风险

### Q8 🔴 热更新（老板硬要求）验收标准缺失
- **老板决策 8**: 热更新硬要求（provider/Agent 改完不重启生效）
- **源码事实**: Agent 改走 HTTP → 能热更新；provider 改走 redux → 理论能热更新（storeSyncService 同步多窗口）
- **缺陷**: "热更新"验收标准未定义（UI 即时变？刷新页面？）；注入改 store 后是否触发 UI 更新未验证
- **调优**: M0 明确验收标准：①改 Agent 名/提示词→UI 即时更新 ②派发 provider→模型下拉即时可选；实测注入改 store 后 UI 响应

### Q9 🔴 Key 保护（R2）与"渲染进程注入"（R1）根本矛盾
- **方案假设**: R2 = 员工端看不到公司模型 Key
- **源码事实**: v1.9.7 provider 数据（含 apiKey）存渲染进程 redux/localStorage；渲染注入（R1 通道）能读写 → 注入脚本本身能看到 Key
- **矛盾**: R1 依赖"渲染能写 provider(含 key)"，R2 要求"渲染不能看 key"——同一渲染进程既能写就能读；无模型网关时 key 必然存员工端 localStorage
- **调优**: 如实说明——锁定 v1.9.x 下 R2 只能"UI 隐藏"（弱），做不到"物理隔离"（强）。**建议 R2 升级为模型网关**（key 藏服务端网关，员工端只配网关 URL，网关转发）

### Q10 🟡 模型网关可能同时解决 R1+R2，但方案没评估
- **源码事实**: v1.9.x 是 OpenAI 兼容客户端，配自定义 provider（base_url 指向网关）即可用公司模型，无需注入改 redux
- **缺陷**: 方案把模型网关列为"备选/兜底"，没意识到可能是 R1+R2 最优解：R1 网关侧控模型列表/可用性，R2 key 全在网关，收回=网关禁用，无需改员工端
- **调优**: 把模型网关从备选**提升为 R1+R2 主方案**。员工端派发一个 `企_网关` provider（URL+无 key），模型由网关控制。需老板拍板

### Q11 🟡 数据采集（R6）合规边界未定义
- **方案假设**: R6 按需采集使用数据，合规已确认
- **缺陷**: 采集字段白名单、脱敏、加密存储、传输加密均未定义；错误日志可能含敏感 prompt；WS 是否 TLS 未定
- **调优**: 定义字段白名单（设备元数据+用量计数+错误类型，不含对话内容）；WS 升级 WSS/TLS；服务端加密存储

### Q12 🟡 补丁版本适配与锁定冲突
- **矛盾**: 若 R7 改锁定 v1.9.x（Q5），则无需多版本补丁库，只需锁死具体小版本
- **缺陷**: 锁哪个小版本未定（188 是 v1.9.7 还是更早？）；list.json key 被掩码层破坏，无法登录验证
- **调优**: 需老板提供 188 真实 API key 或管理员查版本号；统一员工端到 v1.9.7

## 第 3 轮质询（交付 + 运维 + 一致性 + 失败场景靶点）

### Q13 🟡 注入器与 Sidecar 职责边界模糊，升级自愈链条复杂
- **方案假设**: 注入器（一次性改 asar）+ Sidecar（自愈重打）
- **缺陷**: 若 Q2 证实"渲染进程注入"可行，则注入器可退化为纯注入脚本，无需改 asar → 锁死=注入脚本，自愈=重跑注入，无需 asar 补丁库
- **调优**: 放弃改 asar，统一"渲染进程注入"；补丁包只装 Sidecar + 注入脚本（写 userData 非程序目录）；R7 自愈=重跑注入

### Q14 🟡 Sidecar 单点故障——CherryStudio 未启动时无法采集/派发
- **方案假设**: Sidecar 常驻，连接服务端
- **缺陷**: Agent/Provider 管理依赖 CherryStudio API/IPC——未启动时 Sidecar 无法派发/采集；服务端指令积压待重放
- **调优**: 定义"CherryStudio 未启动"状态机——Sidecar 照常连服务端（报 cherry_online:false），指令入队列，启动后再执行

### Q15 🟡 数据一致性——Sidecar 与员工手动修改冲突
- **源码事实**: Agent 走 HTTP 创建；员工若手动删了受管 Agent，managed_registry 仍认为存在，不一致
- **缺陷**: 方案没定义一致性对账
- **调优**: 周期性对账（Sidecar 调 list_agents 比对服务端期望清单：缺的补、受管的保护、非受管的忽略）；结果上报，Web后台可见不一致告警

### Q16 🟡 多设备/多小版本兼容
- **方案假设**: 锁定 v1.9.x
- **缺陷**: 员工端可能 v1.9.0-v1.9.7 任意小版本，agents API 字段可能微差；未定义版本探测/兼容层
- **调优**: 补丁包安装时统一到 v1.9.7（检测非 v1.9.7 则引导装官方 v1.9.7 再打补丁）；Sidecar 上报精确版本，服务端按版本适配

### Q17 🟡 Web 管理后台鉴权缺失（重大安全）
- **方案假设**: 简单 token 鉴权设备连接
- **缺陷**: Web 后台能派发 Agent/模型/锁死规则，若裸奔局域网，任何内网设备能进后台管理所有员工机
- **调优**: Web 后台加管理员登录（账号/SSO）+ 操作审计日志 + 设备 token 可轮换 + request_id 全链路追踪

### Q18 🟡 卸载与残留语义未定义
- **方案假设**: 控制面板可卸载，移除 Sidecar + 恢复标记
- **缺陷**: 卸载后受管 Agent/模型/SKILLS 保留还是删除？注入残留清理？Sidecar 数据删除？
- **调优**: 定义卸载三态：①移除受管（清注入+Sidecar，保留数据）②完全清理（含受管 Agent）③回滚（恢复非受管）。默认建议①，员工离职场景需完全清理（需老板定）

| 主窗口 | Electron 41.2.1, asar | 锁 UI 需注入/源码级 |

## 反向质询（v2 Fork 方案）· 第 1 轮

### Q-A1 🔴 Fork 管理路由鉴权——员工拿到 API key 就能调管理路由
- **源码事实**: v2 所有 /v1 路由共用单 API key（feature.api_gateway.api_key）
- **缺陷**: Fork 加 /v1/admin/* 若复用同一 key，员工知道 key 就能删 Agent/改模型（后门）；若独立 key，要防员工从 Sidecar 配置挖出
- **调优**: 管理路由用独立 managed_key（feature.api_gateway.managed_key），与普通 API key 分离；Sidecar 持管理 key，加密存储不落明文

### Q-A2 🔴 Fork 每个官方版本的适配成本（R7 核心代价）
- **老板决策 B**: 官方更新→适配最新版
- **缺陷**: 官方高频发版（v1.8.4→v2.0.1 20+ 版）；每版可能改 schema/Service 签名/API 结构/UI 组件（锁死注入点漂移）
- **调优**: 按需追（重要功能/安全修复才升）；Fork 用增量 patch（官方原版 + fork diff，升级 rebase）；定义触发升级适配的标准

### Q-A3 🟡 受管泛化——加 managed 列的迁移风险
- **源码事实**: v2 agent/provider 表均无 managed 列；官方受管是硬编码 cherryai
- **缺陷**: 加列涉及 drizzle 迁移，与官方升级迁移叠加可能冲突
- **调优**: 受管标记走旁路表（managed_registry 独立 sqlite），不动官方 schema；官方升级无需迁移自己表，只 rebase 代码 patch

### Q-A4 🟡 锁死 UI 注入点随官方 UI 重构漂移
- **源码事实**: v2 Electron 41 + asar；锁死 UI 需注入 renderer 或改 UI 组件
- **缺陷**: 官方高频重构 UI（v1→v2 大改），注入脚本/组件选择器随版本漂移
- **调优**: 锁死 UI 优先改 Fork 源码组件（renderer 加 managed 判断），源码级锁死更稳；代价每版 rebase。权衡"注入脚本免 rebase 但脆弱 vs 源码级稳但要 rebase"

### Q-A5 🟡 Sidecar 调 Fork 管理路由 vs 直连 DataApi
- **源码事实**: v2 管理走内部 IPC DataApi（非 HTTP），Fork 路由需包装 DataApi Service
- **缺陷**: 部分操作（会话/采集）DataApi 可能无方法需 Fork 补；管理路由与 DataApi 权限模型不一致
- **调优**: 管理路由只暴露服务端/Sidecar 需要操作（agent/provider/skill/mcp CRUD），不全量镜像；复用 DataApi 受管保护（managed 项在管理路由也拒改）

### Q-A6 🟡 更新适配链路（Fork 安装包怎么推给员工）
- **老板决策 B**: 官方更新→适配最新版
- **缺陷**: 官方发版→rebased fork→重构建 Windows 包→推更新通道，需自动化否则每次手动
- **调优**: 自动构建流水线（官方 release 触发→自动 rebase fork→构建→上传更新通道）；员工端 Sidecar 轮询 Fork 更新通道（替代官方 feedURL）自动升级

## 反向质询（v2 Fork 方案）· 第 2 轮

### Q-A7 🔴 花费监控"异常停 key"——无可执行细节
- **老板决策 A**: 用中转实时监控花费，异常停 key 重建
- **缺陷**: 方案只有"监控"二字；数据源/异常判定/停 key 自动or手动/key 重建流程未定义
- **调优**: 定义完整模块：①花费数据源（中转账单 API 定时拉取）②异常判定（阈值/增速/单设备超限）③停 key（自动停+告警，人工确认重建）④重建（中转新建 key→Fork 管理路由更新员工端 provider）

### Q-A8 🟡 停 key 后员工端连锁反应
- **源码事实**: v2 provider key 存 user_provider 表（Fork 管理路由可写）
- **缺陷**: 停 key 重建后需重新派发；进行中会话中断；若员工自己改了 provider，推 key 会覆盖吗
- **调优**: 端到端流程——中转停旧 key→新建 key→Fork 管理路由只更新受管 provider 的 key 字段（不动员工自配）→热更新；定义降级策略（员工暂时用自配模型）

### Q-A9 🟡 花费监控与 R6 采集数据源重叠
- **缺陷**: 中转账单（真实花费）vs 员工端上报（本地估算）两套数据可能重复/不一致，以哪个判异常
- **调优**: 花费监控以中转账单为准（权威）；R6 员工端上报只用于设备健康/功能使用，不做花费判定数据源

### Q-A10 🟡 Sidecar 与 Fork 部署关系未明确
- **缺陷**: Sidecar 独立进程还是 Fork 内置模块未定；自启动/生命周期管理未定
- **调优**: Sidecar 做独立进程（NSSM 注册 Windows 服务），与 Fork 解耦——Fork 升级不影响 Sidecar，反之亦然；Sidecar 通过 Fork 管理路由 + WS 连服务端

### Q-A11 🟡 Fork 版 vs 官方版升级冲突
- **缺陷**: 员工已装官方版，Fork 覆盖还是共存；更新通道冲突；卸载能回滚官方版吗
- **调优**: Fork 版覆盖安装官方版（userData 数据目录保留，程序目录换 Fork）；禁用官方更新通道（改 feedURL 指向自建）；卸载提供回滚官方版能力；数据目录独立于程序目录是前提

### Q-A12 🟡 Web 后台需加花费监控面板
- **源码事实**: Web 后台管理派发/锁死/采集
- **缺陷**: 决策 A 引入花费监控后，后台需加花费看板（排行/告警/停 key 操作），方案没规划
- **调优**: Web 后台新增花费监控模块——实时看板、阈值告警、异常高亮、停 key/重建按钮；鉴权+操作审计

## 反向质询（v2 Fork 方案）· 第 3 轮

### Q-A13 🟡 Fork 版 Windows 安装包构建链路（跨平台）
- **源码事实**: v2 Electron 41 + electron-builder；本机 Linux 无 Wine/Windows 打包链
- **缺陷**: 本机无法构建 Windows 安装包；每次官方更新适配后都要重包
- **调优**: 用 GitHub Actions windows-latest runner 自动构建（官方 release 触发→checkout fork→electron-builder 出 Windows 包→上传更新通道）；本机 Linux 只做代码开发和 patch 维护

### Q-A14 🔴 Fork 管理路由热更新未验证（直接关系老板硬要求）
- **老板决策 8**: 热更新硬要求（改完不重启生效）
- **源码事实**: v2 DataApi 有事件（emitAgentCreated/emitAgentUpdatedForIds）
- **缺陷**: Fork 管理路由写 sqlite 后，渲染 UI 是否实时刷新未验证；需复用 DataApi 事件广播机制
- **调优**: M0 实测——Fork 管理路由 create/update agent/provider 后渲染 UI 是否即时更新（调 emitAgentCreated 等触发 UI）；这是热更新技术前提

### Q-A15 🟡 Fork 管理路由直写 sqlite 的锁/事务风险
- **源码事实**: v2 drizzle + libsql 单连接 + WAL + 写门控
- **缺陷**: 绕过 DataApi Service 直写会绕过事务/校验（createAgentTx 的 insertWithOrderKey/assertSkillsExistTx），数据不一致或锁冲突
- **调优**: Fork 管理路由必须复用 AgentService/ProviderService 公开方法，不直写 sqlite；仅官方无方法时才补，且遵循同样事务模式

### Q-A16 🟡 员工自配模型（R1 共存）与受管模型边界
- **源码事实**: v2 provider 表 + userModel 表；员工可自配
- **缺陷**: 受管保护需区分受管 provider 和员工自配 provider；边界判定靠什么
- **调优**: managed_registry 记录受管 provider/agent id；Fork 管理路由+渲染层据此判断可管/不可管；员工自配（不在 registry）完全自由；企_ 前缀仅作命名约定，真正控制靠 registry

### Q-A17 🟡 数据采集 R6 的"按需"触发机制未定义
- **缺陷**: "按需采集"没定义触发条件（服务端主动拉?定时上报?事件触发?）
- **调优**: Sidecar 定时上报设备健康/用量计数（低频 5 分钟）+ 服务端按需拉详细数据（排查时报错日志）；字段白名单不含对话内容

### Q-A18 🟡 失败场景——升级失败/Sidecar 失联/服务端宕机
- **缺陷**: 方案 10.x 覆盖正常路径，失败场景未系统化
- **调优**: ①Fork 升级失败→回滚上一版（保留备份）②Sidecar 失联→心跳超时告警，设备标记离线 ③服务端宕机→员工端功能不受影响（服务端非运行依赖），恢复后 Sidecar 补传队列

## 反向质询（v2 Fork 方案）· 第 4 轮（纯验证收尾）

### Q-A19 🔴 热更新需 Fork 自建"写入→UI 刷新"链路（实锤）
- **源码事实**: v2 onAgentCreated/onAgentUpdated 事件只有 AgentSessionRuntimeService 订阅（会话运行时）；无主进程→渲染进程 UI 实时刷新链路；官方 Agent 管理走 DataApi（渲染调 IPC，返回值驱动 UI），官方不需要服务端推事件
- **缺陷**: Fork 管理路由是服务端/Sidecar 侧写 sqlite，渲染 UI 不会感知 → 改完不刷新，热更新不成立
- **调优**: Fork 必须自建"写入→UI 刷新"链路——管理路由写 sqlite 后通过 IPC 向渲染广播"数据已变更请刷新"（或复用 redux storeSyncService）；**M0 必测**；做不出则热更新不成立，需如实汇报并降级为"改完手动刷新/重启"

### Q-A20 🟡 Fork 管理路由写 sqlite + 通知 UI 双写一致性
- **源码事实**: 官方 DataApi 是"渲染调 IPC→Service 写 sqlite→返回值→渲染更新 store"单线程闭环
- **缺陷**: Fork 管理路由打破闭环——服务端写入不经过渲染进程，UI 与服务端状态可能短暂不一致
- **调优**: 写完 sqlite 主动广播 UI 刷新事件让渲染重拉；或提供强制刷新入口；定义 UI 刷新延迟可接受范围

### Q-A21 🟡 Fork 版本选择——基于哪个官方版本起 Fork
- **源码事实**: 当前 clone v2.0.1（main @ f39b17d）
- **缺陷**: Fork 基线选 v2.0.1 还是最新稳定版未定
- **调优**: 以官方最新稳定版为 Fork 基线（起 Fork 前拉官方最新）；分支策略 official/xxx（官方镜像）+ managed/xxx（Fork 改动），官方更新 rebase managed 分支
