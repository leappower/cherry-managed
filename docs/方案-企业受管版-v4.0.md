## 〇、v4.0 相对 v3.1 的核心变化（方向反转）

| 维度 | v3.1（旧，已废弃） | v4.0（最终定案） |
|------|------------------|-----------------|
| 员工端版本 | **锁定 v1.9.x**（老板旧拍板） | **跟随官方最新**（老板重拍板，推翻） |

| 适配策略 | 锁死小版本免适配 | **官方更新 → 我们适配最新版**（增量 patch + 按需升级） |

## 一、需求定义（R1-R7）

### R1 · 模型统一管控
- **定义**：公司统一管理员工可用的公司模型，可派发、可收回。
- **强化点**：
  1. 远程端派发**公司模型列表**（`企_` 前缀隔离）；
  2. 可**收回**（删除受管 provider 或禁用其 key）；
  3. **员工仍可自配其他模型不受影响**（双向并存，员工自配不在 managed_registry 中，完全自由）。
- **实现层**：Fork 管理路由 `/v1/admin/providers` + Sidecar 派发 + managed_registry 隔离。

### R2 · Key 保护
- **定义**：员工端**看不到**公司派发模型的 Key 原文。
- **实现方式**（定案：不用模型网关）：
  1. **UI 锁死**：Fork 源码级隐藏公司受管 provider 的 apiKey 字段显示，员工无法查看/编辑；
  2. **兜底**：服务端**花费监控**实时聚合，异常（超阈值/超速/单设备超限）→ **停 key 重建**（中转侧停用旧 key、新建 key、Fork 管理路由只更新受管 provider 的 key 字段）→ 热更新。
- **诚实边界**：无模型网关时，key 必然物理存在于员工端 sqlite（user_provider 表）。R2 落地为「UI 不可见 + 异常停 key 兜底」，**做不到物理隔离**（已如实向老板说明并获认可）。
- **中转侧边界（老板新拍板）**：中转 = 第三方中转服务商（如 OpenAI 兼容中转平台），key 归中转侧持有，Fork 管理路由**无法控制中转侧 key 停用**；停 key 走中转侧对接通道（中转侧 API 停用/授权接口，否则人工兑底），Fork 仅更新员工端 provider 的 key 字段（详见 7.4）。

### R3 · Agent 远程管理
- **定义**：远程派发 Agent **开箱即用**，支持**收回 / 禁用 / 升级**。
- **Agent = MCP + SKILL + 预设数据文件**完整打包（agent-package.zip）。
- **实现层**：Fork 管理路由 `/v1/admin/agents`（对接 AgentService 完整 CRUD）+ Sidecar 派发。

### R4 · SKILLS 派发 + 版本管理
- **定义**：支持 **Bootstrap、SKILLS 版本、MCP**，可回收 / 升级。
- **实现层**：Fork 管理路由 `/v1/admin/skills` + `/v1/admin/mcp` + 服务端 skills_repo（版本仓库）+ Sidecar 派发。

### R5 · 锁死 UI
- **定义**：员工端设置页，远程端管理的（模型 / MCP / SKILLS / Agent）**锁死或隐藏**；**锁死规则可远程迭代**。
- **实现层**：Fork 源码级改渲染组件加 `managed` 判断（隐藏删除按钮 / 只读）+ `lock_rules.json` 远程迭代（机制固定 + 规则远程拉取）。

### R6 · 数据采集（对整个智能体工作目录管理）
- **定义**：Sidecar 采集 → 服务端分析。**采集范围 = 整个智能体工作目录**（Agent 的上下文、产出内容、数据文件全部在内），不只用量计数。这是合规的，因为 CherryStudio 是企业工作软件，公司对员工工作产生的上下文与产出拥有管理权。
- **实现层**：
  1. Fork 管理路由 `/v1/admin/usage` 读员工端 `ai_usage_record` 表（模型+token 用量，供花费监控/设备健康）；
  2. **工作目录采集**：通过 Agent 的 `accessible_paths`（Agent 可访问路径，方案 4.2/6.2 已定义）读取智能体工作目录内的上下文与产出内容（对话记录、生成文件、数据文件等），Fork 加 `/v1/admin/agent-files` 路由（按 agent_id/路径枚举+读取）→ Sidecar 按需拉取上报服务端数据仓库；
  3. 采集触发：**按需**（服务端发起/排查时），非主动常驻上报。
- **合规边界（老板纠正 2026-08-07）**：采集含**上下文与产出内容**（工作目录全量），非仅用量；因 CherryStudio 为工作软件，公司有权管理员工工作产出。传输走 WS 2334（可升级 WSS/TLS）；服务端加密存储；采集范围限 Agent 工作目录（`accessible_paths` 内），**不越权读取工作目录之外的个人文件**。

### R7 · 升级免疫
- **定义**：员工自己升级**不破坏受管状态**；官方更新后我们的 Fork 自动适配。
- **实现层（定案）**：
  1. **禁用官方更新通道**：Fork 改 `feedURL`（electron-updater generic provider，从 `https://releases.cherry-ai.com` 指向自建更新通道）；
  2. **Fork 增量 patch**：官方原版 + fork diff，官方更新 rebase managed 分支；
  3. **按需升级节奏**：重要功能 / 安全修复才追官方新版（触发标准见 D19）；
  4. **构建流水线**：GitHub Actions windows-latest 自动构建 → 推自建更新通道 → Sidecar 轮询升级。

### 2.1 Fork 层（改官方最新版 cherry-studio 本体）— 核心

职责：为 Sidecar / 服务端提供受管管理通道，锁死员工 UI，接管更新。

| 模块 | 职责 | 落地要点 |
|------|------|---------|
| **管理路由 `/v1/admin/*`** | agents/providers/skills/mcp/usage 的 CRUD + 读取 | 在官方 `v1Routes` Elysia 插件链追加 `adminRoutes`；复用 AgentService/ProviderService 方法，**不直写 sqlite**（规避写门控/锁库/事务风险） |
| **独立管理 key** | `feature.api_gateway.managed_key`，与普通 API key（`feature.api_gateway.api_key`）分离 | Sidecar 持管理 key，加密存储不落明文；管理路由走独立 bearer 鉴权 |
| **泛化受管保护** | 把官方硬编码 `cherryai`（`assertManagedCherryAiProviderMutationAllowed` / `isManagedCherryAiProviderId`）泛化为 managed_registry 判定 | 受管 provider/agent 在管理路由与渲染层均不可改/删；员工自配（不在 registry）完全自由 |
| **热更新 IPC 刷新广播** | 管理路由写 sqlite 后，向渲染进程广播「数据已变更请刷新」 | 写 sqlite → IPC 广播 → 渲染进程 TanStack Query `invalidateQueries('/agents')` 刷新 UI（复用官方 useDataApi 机制） |
| **锁死 UI（源码级）** | 渲染组件加 `managed` 判断：隐藏删除按钮 / 受管项只读 / 隐藏 apiKey 显示 | 改 Fork 渲染组件（Sessions.tsx 删除 `canDelete`、Provider 删除 `useProviderDelete`、key 显示字段等） |
| **禁用官方更新通道** | 改 `feedURL` 指向自建更新通道 | `electron-builder.yml` publish 改 generic provider url → 自建 feed；`autoUpdater.channel` 接管 |
| **usage 管理路由** | 读 `ai_usage_record` 表（providerId/modelId/inputTokens/outputTokens/totalTokens/sourceType） | 供 Sidecar 定时拉取上报 |

### 2.2 Sidecar 层（独立进程，NSSM Windows 服务）— 常驻执行器

职责：连服务端 WS + 调 Fork 管理路由 + 派发 + 采集 + 对账 + 自愈。

| 模块 | 职责 | 落地要点 |
|------|------|---------|
| **WS 客户端** | 连服务端 2334，长连接，心跳 | 断线重连 + 指数退避；重连后补传未确认指令 |
| **Fork 管理路由客户端** | 调本地 Fork `/v1/admin/*`（HTTPS 127.0.0.1） | 用独立管理 key 鉴权 |
| **派发执行器** | 派发 Agent/模型/SKILLS（幂等） | 每指令带 request_id，执行后回执；断线重发不重复创建 |
| **usage 采集上报** | 定时拉 `/v1/admin/usage` → 汇总上报服务端 | 低频（5 分钟）；字段白名单（用量） |
| **工作目录采集** | 按服务端指令拉 `/v1/admin/agent-files`（Agent 工作目录上下文+产出）→ 上报 | 限 accessible_paths 内，不越权读取工作目录外个人文件 |
| **对账** | 调 `list_agents` 比对服务端期望清单 | 缺的补、受管的保护、非受管的忽略；结果上报（Web 后台可见不一致告警） |
| **受管标记旁路表** | 本地 `managed_registry.db`（sqlite），Sidecar 唯一写者 | 记录 id→managed 映射；不动官方 schema，无迁移锁库风险 |
| **自愈** | Fork 升级失败回滚上一版；注入失败重跑 | 保留上一版备份；Sidecar 与 Fork 解耦互不影响 |
| **NSSM 服务注册** | Windows 服务，开机自启，崩溃自愈 | 与 Fork 解耦；CherryStudio 未启动时 Sidecar 照常连服务端（报 cherry_online:false） |

### 2.3 服务端（server/ · 端口 2334 · FastAPI）— 统一调度中枢

| 模块 | 职责 |
|------|------|
| **Web 管理后台** | 管理员登录（账号鉴权）+ 操作审计日志（谁在何时做了何操作）；设备/Agent/模型/SKILLS/锁死规则/花费看板管理 |
| **花费监控模块** | `ai_usage_record` 聚合看板 + 异常告警（阈值/增速/单设备超限）+ 停 key 重建流程 + **中转服务对接**（中转侧 key 停用/授权通道） |
| **agents_lib** | Agent 模板库 + 版本管理（Agent 打包上传 → 下发） |
| **skills_repo** | SKILLS 包上传 + 版本管理 + 下发 |
| **lock_rules** | 锁死规则生成 + 下发（机制固定 + 规则远程迭代） |
| **gitbash_repo** | Git Bash 安装包托管 + 远程安装指令 |
| **patch_repo** | Fork 安装包 + 补丁库（增量 patch） |
| **设备注册表** | device_id + token + 状态（在线/离线）+ 分组 |
| **数据仓库** | 员工端用量聚合存储（SQLite 起步 → PostgreSQL 规模化） |

## 三、管理路由 API 设计（`/v1/admin/*`）

> 鉴权：独立管理 key（`feature.api_gateway.managed_key`），bearer 比对（timing-safe）。与普通 API key 分离，员工拿到普通 key 也无法调管理路由。
> 实现：在官方 `v1Routes` Elysia 插件链追加 `adminRoutes` 插件，复用各 Service 公开方法，不直写 sqlite。

### 3.1 Agent 管理（对接 AgentService CRUD）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/v1/admin/agents` | 创建 Agent（createAgentWithId），body 含 name/type/model/instructions/configuration/tools/skills，`managed:true` 写入旁路表 |
| GET | `/v1/admin/agents` | 列出全部 Agent（listAgents），含 managed 标记 |
| GET | `/v1/admin/agents/:id` | 查看单个（getAgent） |
| PUT | `/v1/admin/agents/:id` | 全量更新（updateAgent），受管项校验 |
| DELETE | `/v1/admin/agents/:id` | 删除（deleteAgent）——受管保护：非 managed_registry 写者不可删受管项 |
| POST | `/v1/admin/agents/:id/disable` | 禁用（软删/下架），员工端不可见不可用 |
| POST | `/v1/admin/agents/reorder` | 排序（reorder） |

### 3.2 Provider / 模型管理（对接 ProviderService CRUD）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/v1/admin/providers` | 创建 provider（create），含 base_url/type/models |
| POST | `/v1/admin/providers/batch-upsert` | 批量写入（batchUpsert） |
| PUT | `/v1/admin/providers/:id` | 更新（update）——受管保护：只更新受管 provider，不动员工自配 |
| DELETE | `/v1/admin/providers/:id` | 删除（delete）——受管项仅服务端可删 |
| POST | `/v1/admin/providers/:id/api-keys` | 加 key（addApiKey）——**停 key 重建流程用** |
| PUT | `/v1/admin/providers/:id/api-keys` | 替换 key（replaceApiKeys）——**重建后推新 key** |
| DELETE | `/v1/admin/providers/:id/api-keys` | 删 key（deleteApiKey）——**仅删员工端 provider 的 key 字段**（key 归中转侧持有，Fork 无法停用中转侧 key，见 7.4） |

### 3.3 SKILLS / MCP 管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET/POST/PUT/DELETE | `/v1/admin/skills` | agent_skill 表 CRUD + 版本写 agent_global_skill |
| GET/POST/PUT/DELETE | `/v1/admin/mcp` | mcp_server 表 CRUD |

### 3.4 Usage / 工作目录读取（供 Sidecar 采集）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/v1/admin/usage` | 读 `ai_usage_record` 表（providerId/modelId/inputTokens/outputTokens/totalTokens/sourceType），支持时间窗/设备过滤 |
| GET | `/v1/admin/agent-files` | 枚举+读取智能体工作目录（accessible_paths 内）上下文与产出内容，按 agent_id/路径过滤——R6 工作目录采集通道 |

### 3.5 受管保护语义（泛化）

- `isManaged(id)` → 查旁路表 managed_registry；
- 管理路由对受管项的变更请求需校验请求方为 Sidecar/服务端（管理 key 本身就保证）；
- 渲染层对受管项隐藏删除/编辑（见第五节锁死 UI）；
- 员工手动改（绕过管理路由）由 Sidecar 对账发现并修复。

## 四、WS 通信协议（服务端 ↔ Sidecar，端口 2334）

> 服务端 WS 框架：`websockets`；Sidecar 客户端：`websocket-client`。JSON 消息，`type` 区分。

### 4.1 设备注册（Sidecar → 服务端）
```json
{
  "type": "register",
  "device_id": "HOST_CHEN-001",
  "hostname": "HOST_CHEN",
  "os": "windows",
  "cherry_version": "2.0.1",
  "fork_version": "4.0.0-rc.1",
  "git_bash_installed": false,
  "git_bash_version": null,
  "token": "***"
}
```

### 4.2 派发 Agent（服务端 → Sidecar）
```json
{
  "type": "dispatch_agent",
  "action": "create",
  "agent": {
    "name": "企_客服助手",
    "managed": true,
    "model": "企_DeepSeek:deepseek-v4-flash",
    "instructions": "...",
    "accessible_paths": ["D:\\...\\Agents\\deployed"],
    "configuration": {"permission_mode": "bypassPermissions", "max_turns": 100},
    "tools": ["web_search", "bash"],
    "skills": ["skill-a@v1.2", "skill-b@v2.0"]
  },
  "package_url": "http://server/agents/企_客服助手/v3.zip",
  "request_id": "req-001"
}
```

### 4.4 锁死规则同步（服务端 → Sidecar，R5）
```json
{

  "rules": {
```

## 五、热更新机制设计（IPC 刷新广播链路）

**技术前提（M0-1 实测）**：官方 v2 的 Agent/Provider 管理走 DataApi（渲染进程调 IPC → Service 写 sqlite → 返回值驱动 UI），**官方没有「服务端/Sidecar 侧写 sqlite → 渲染 UI 实时刷新」的现成链路**。渲染进程用 TanStack Query（`useDataApi`），数据刷新靠 `invalidateQueries('/agents')`。因此 Fork 必须**自建「写入 → UI 刷新」链路**。

### 5.1 链路（方案 A）
```
Fork 管理路由（服务端/Sidecar 侧）
   │ 写 sqlite（复用 AgentService/ProviderService 方法，触发官方内部变更事件）
   ▼
主进程 补 IPC 刷新广播（新增 channel，如 `data-changed`，携带刷新目标）
   ▼
渲染进程 监听广播 → 对相应 query key 调 invalidateQueries('/agents' | '/providers' | ...)
   ▼
TanStack Query 重新拉取 → UI 即时刷新（不重启）
```

### 5.2 验收标准（M0-1 必测）
1. 改 Agent 名/提示词 → UI 即时更新；
2. 派发 provider → 模型下拉即时可选；
3. 停 key 重建推新 key → 受管 provider 生效，员工端无需重启。

### 5.3 兜底（方案 C）
- 若 IPC 广播链路实测做不出（M0-1 失败），**降级为「强制重启兜底」**：管理路由写完 sqlite 后，触发 CherryStudio 主进程重启（或提示员工重启）；
- 热更新为老板硬要求，方案 A 优先；方案 C 仅作技术兜底，需如实汇报。

### 5.4 一致性
- 管理路由写完 sqlite 主动广播 UI 刷新，UI 短暂延迟（秒级）可接受；
- Sidecar 周期性对账兜底，修复 UI 与服务端不一致。

## 六、锁死 UI 设计（源码级 managed 判断 + lock_rules 远程迭代）

### 6.1 两层设计
- **机制固定（源码级）**：Fork 渲染组件加 `managed` 判断，受管项隐藏删除按钮 / 只读 / 隐藏 apiKey。此机制在 Fork 源码编译期固定，随 Fork 版本更新。
- **规则远程迭代**：`lock_rules.json` 从服务端拉取，控制「哪些页面锁 / 隐藏哪些字段 / 只读哪些字段」等**策略参数**（非机制本身）。改后端即可迭代锁死范围，不重发 Fork 包。

### 6.2 源码级 managed 判断注入点（v2.0.1 已核清）

> ⚠️ **注入点基线提醒（v4.0 补充）**：下表注入点基于当前 v2.0.1 源码核清，官方 UI 重构会导致注入点漂移。**实施时（F-10）必须重新拉取 M0-3 的最新官方基线，逐项重新核对下述注入点行号/组件路径，不直接套用下表现状行号**。若官方已重构相关组件，以下表为起点重新定位等价注入点。
| 位置 | 官方现状 | Fork 改法 |
|------|---------|----------|
| Agent 删除按钮 | `Sessions.tsx` `canDelete={!!workspaceId}` | 加 `&& !isManaged(agent.id)` |
| Agent 编辑 | Agent 配置页可改 | 受管项只读（disabled） |
| Provider 删除 | `useProviderDelete.ts` → `deleteProviderById` | 受管 provider 不显示删除入口 |
| Provider Key 显示 | 渲染层显示 apiKey 原文 | 受管 provider 隐藏/掩码 key 字段（R2） |
| SKILLS / MCP 删除 | 设置页可删 | 受管项隐藏删除入口 |
| Model 下拉 | provider.models 可选 | 受管 provider 模型列表由服务端控制 |

### 6.3 受管判定
- 渲染层经 preload 暴露的 IPC 读旁路表 `managed_registry.db`（Sidecar 唯一写者）；
- `isManaged(id)` 查旁路表；受管项（在 registry）→ 锁死；员工自配（不在 registry）→ 完全自由。

## 七、花费监控模块详细设计（R2 兜底核心）

### 7.1 数据源
- **权威数据源**：员工端 `ai_usage_record` 表（v2 原生记录每条 AI 调用的 providerId/modelId/inputTokens/outputTokens/totalTokens/sourceType）；
- Fork 加 `/v1/admin/usage` 路由读出；Sidecar 定时拉取 → 上报服务端数据仓库；
- **判定口径**：以员工端上报的用量计数为基准（**老板决策 A 已确认**走员工端表，而非中转账单）。
- **中转侧边界（老板新拍板）**：中转 = 第三方中转服务商（如 OpenAI 兼容中转平台）。因此 **key 归中转侧持有**，Fork 管理路由**无法控制中转侧的 key 停用**（`/v1/admin/providers/:id/api-keys` 只能更新员工端 provider 的 key 字段，管不到中转侧）。停 key 需设计中转侧对接通道（授权/停用接口）或人工兑底（详见 7.4）。

### 7.2 聚合看板（Web 后台）
- 按 provider / model / 设备 / 时间聚合；
- 展示：总 token、估算花费（单价表配置）、设备排行、模型排行；
- 异常高亮（红色标记触发阈值项）。

### 7.3 异常判定规则（多维度，防误判）
| 规则 | 说明 | 触发 |
|------|------|------|
| **单设备超限** | 某设备累计 token/花费超设定阈值 | 阈值可配（如单设备日花费 > X 元） |
| **增速异常** | 某设备/模型 token 增速超正常波动（环比/同比） | 增速 > 设定倍数 |
| **总额超限** | 全公司某 provider/model 累计超预算 | 预算阈值 |
| **关键模型异常** | 某企_模型被高频调用（疑似滥用） | 调用频次超限 |

### 7.4 停 key 重建流程
```
1. 触发异常（单设备超限/增速异常/总额超限）
2. 服务端告警（Web 后台高亮 + 通知管理员）
3. 管理员确认（人工确认重建，防误判）
4. 停旧 key：**走中转侧对接通道停用**该设备对应的企_ provider key
   └── 中转侧对接通道（老板拍板：key 归第三方中转侧持有，Fork 管不到中转侧 key）：
       ├── 优先：中转侧管理 API（若第三方提供 /admin 停用/授权接口，经服务端中转对接模块调用）
       └── 兜底：人工在中转平台停用（无管理 API 时）
   ⚠️ Fork `/v1/admin/providers/:id/api-keys` 只能更新员工端 provider 的 key 字段，**不能停用中转侧 key**
5. 新建 key：中转侧新建 key
6. 推新 key：Fork `/v1/admin/providers/:id/api-keys` PUT replaceApiKeys
   └── 只更新受管 provider 的 key 字段，不动员工自配（推的是中转侧新 key，使员工端指向新 key）
7. 热更新：IPC 广播 → 受管 provider 生效
8. 回执 + 审计日志
```

### 7.5 降级策略
- 停 key 期间员工暂时用自配模型（R1 双向并存的天然缓冲）；
- 进行中会话中断（可接受，异常滥用场景）；
- 重建为手动确认（人工判断），不自动盲目停 key；
- **中转侧停 key 兑底**：若中转侧无管理 API（不能自动停用），停 key 退化为「人工在中转平台停用 + 服务端生成停工单向管理员并回填确认」，停用完成前该设备企_ provider 可能仍可用——如实记录该兑底窗口。

### 7.6 与 R6 采集的关系
- 花费监控**复用**员工端 `ai_usage_record`（同一数据源，模型+token 用量）；
- **R6 采集 = 工作目录全量管理**：除用量计数外，还采集 Agent 工作目录内（`accessible_paths`）的上下文与产出内容——对话记录、生成文件、数据文件，经 Fork `/v1/admin/agent-files` 路由按需读取上报；
- 花费监控（用量）与工作目录采集（内容）走同一套采集上报链路（Sidecar + WS 2334），字段/范围不同但统一由服务端控制触发；
- 合规依据：CherryStudio 为企业工作软件，公司对员工工作产出的管理权覆盖上下文与产出内容（老板 2026-08-07 纠正）。
