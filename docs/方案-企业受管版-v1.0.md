# CherryStudio 企业受管版 · 完整方案 v1.0

> 状态: 已确认 | 最后更新: 2026-08-06
> 负责人: 鮱澄军团（主 Agent 调度）
> 目标: 公司内部 CherryStudio 企业受管分发系统

---

## 一、目标（一句话）

给公司内部做「CherryStudio 企业受管版」：**公司统一派发模型/Agent/SKILLS/MCP，员工端这些受管项锁死不能改，但员工仍可自配自己的模型；公司模型 Key 不泄露；数据回采驱动 Agent 进化；员工自己升级不破坏受管状态。**

---

## 二、需求清单（R1-R7，最终版，已强化）

| # | 需求 | 强化点 | 实现层 |
|---|------|--------|--------|
| R1 | **模型统一管控** | ①远程端派发**公司模型列表**；②可**收回**；③**员工仍可自配模型不受影响**（双向并存） | Sidecar + Fork |
| R2 | **Key 保护** | 员工端**看不到**公司派发模型的 Key 原文 | 模型网关 / UI锁 |
| R3 | **Agent 远程管理** | 派发 Agent **开箱即用**，支持**收回/禁用/升级**；Agent=**MCP+SKILL+预设数据文件**完整打包 | Sidecar |
| R4 | **SKILLS 派发+版本管理** | 支持 **Bootstrap、SKILLS 版本、MCP**，可回收/升级 | Sidecar |
| R5 | **锁死 UI** | 员工端设置页：**远程端管理的（模型/MCP/SKILLS/Agent）锁死或隐藏** | Fork |
| R6 | **数据采集** | Sidecar 采集使用数据 → 服务端分析 → 驱动进化 | Sidecar |
| R7 | **升级免疫** | 员工自己升级**不破坏受管状态** | Fork + 更新接管 |

## 三、架构（两层分工）

```
┌───────────── 管理服务端 (对外 23333) ─────────────┐
│  · 模型 Provider 仓库（统一配置、集中发 key/网关）  │
│  · Agent 模板库 + SKILLS 版本管理                 │
│  · 使用数据仓库（采集→分析→进化闭环）              │
│  · 派发调度 + 更新服务                            │
└──────────▲───────────────────────────▲───────────┘
           │ HTTPS/WS 主动连接           │ HTTPS/WS
┌──────────┴──────────┐      ┌──────────┴──────────┐
│ 员工设备 A           │ ... │ 员工设备 N           │
│  ┌──────────────┐   │      │  ┌──────────────┐   │
│  │ CherryStudio │   │      │  │ CherryStudio │   │
│  │ (Fork版·UI锁死)│  │      │  │ (Fork版·UI锁死)│  │
│  └──────▲───────┘   │      │  └──────▲───────┘   │
│         │ 本地调用    │      │         │ 本地调用   │
│  ┌──────┴───────┐   │      │  ┌──────┴───────┐   │
│  │  Sidecar     │   │      │  │  Sidecar     │   │
│  │ (常驻受管进程)│   │      │  │ (常驻受管进程)│   │
│  └──────────────┘   │      │  └──────────────┘   │
└─────────────────────┘      └─────────────────────┘
```

### A. Fork 层（改 CherryStudio 本体）→ 锁死 + 受管
| 改动点 | 内容 | 作用 |
|--------|------|------|
| ① UI 锁死 | 设置页 provider/model/mcp/skills/agent 受管项只读/隐藏 | R5 |
| ② UI 锁死 | 隐藏公司模型 API Key 显示 | R2 |
| ③ 入口接管 | 禁用原生更新按钮 | R7 |
| ④ 配置注入 | `feature.api_gateway.host=127.0.0.1` 固定 | 只允许本地 Sidecar 访问 |
| ⑤ 受管开关 | `config.json` 加「受管标记」，UI 检测即锁死 | 一个版本两种模式 |

### B. Sidecar 层（不改本体）→ 实时控制 + 数据闭环
| 能力 | 作用 |
|------|------|
| ① 服务端对接 | 主动 HTTPS/WS 连服务端（绕开局域网转发限制） |
| ② Agent/SKILLS 派发+回收 | 通过本地 127.0.0.1:23333 调 API / 写数据目录 [待实测热更新] |
| ③ 完整性校验 | 校验 Fork 版文件哈希，被覆盖→报警/重打/上报 |
| ④ 数据采集 | 会话摘要、使用频次、报错 → 上报服务端 |
| ⑤ 开机自启+自愈 | 掉线重连、转发自愈 |

## 四、四个求证点的最终结论（已和老板确认）

| # | 求证点 | 结论 | 影响 |
|---|--------|------|------|
| Q1 | provider 是否分离存储 | **不依赖**。用「企_」前缀命名隔离企业模型 | 简化 R1 |
| Q2 | 能否热更新 | **硬要求，必须热更新**（改完不重启生效） | 派发走 API/内部服务，不能只改文件+重启 [待实测] |
| Q3 | config 单向锁 | **不需要**。UI 锁死足够 | 简化 R5 |
| Q4 | 官方未文档化 API | **留扩展位**，支持后续迭代 | 架构要可扩展 |

> ⚠️ Q2「热更新」是当前唯一技术不确定点，M0 阶段必须实测验证。

## 五、关键设计决策

### D1 企业模型命名隔离（R1）
- 企业派发模型统一加前缀 `企_`（如 `企_DeepSeek`）
- 员工自配模型自由命名，互不干扰
- 收回时从预设层移除 `企_` 前缀项

### D2 Key 保护双保险（R2）
- 强方案：公司模型走**模型网关**，员工端只看到网关 URL，Key 藏网关侧
- 兜底：UI 锁死隐藏 Key 显示

### D3 Agent 完整打包（R3）
```
agent-package/
├── agent.json            # Agent 定义
├── skills/               # SKILLS 目录
├── mcp/                  # MCP 配置
└── data/                 # 预设数据文件
```
- 服务端版本管理，Sidecar 按版本同步

### D4 SKILLS 版本仓库（R4）
- 复用 NAS 分发思路（SKILL经验蒸馏.md）系统化
- `skills-repo/{name}/{version}/`
- Sidecar 拉取指定版本 → 写员工端 `.claude/skills`

### D5 自进化双路径（R6）
- ① 预设 SKILLS（Agent 自带进化逻辑）
- ② 服务端数据闭环（采集→分析→开发新 Agent/SKILLS 回推）
