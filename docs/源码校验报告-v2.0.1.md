## 二、关键源码证据

### 2.1 官方 API Gateway 路由清单（app.ts）

`src/main/features/apiGateway/app.ts` 挂载的 `/v1` 路由：
```
messagesRoutes   → POST /v1/messages
chatRoutes       → POST /v1/chat/completions
responsesRoutes  → POST /v1/responses
modelsRoutes     → GET  /v1/models（只读列表）
knowledgeRoutes  → GET  /v1/knowledge-bases, POST /v1/knowledge-bases/search
geminiRoutes     → /v1beta/models/{model}:generateContent
```

**无 `/v1/agents`、`/v1/providers`、`/v1/skills`、`/v1/mcp` 任何管理路由。**

鉴权：`@elysia/bearer` + `authorizeApiRequest`（x-api-key / Bearer / Gemini key），`crypto.timingSafeEqual` 比对。

### 2.2 数据存储（SQLite）

- 数据库：`{userData}/Data/cherrystudio.sqlite`（`pathRegistry.ts:91`）
- 引擎：better-sqlite3 单连接 + WAL（`DbService.ts:51`）
- 表：`agent`、`user_provider`、`agent_skill`、`agent_global_skill`、`mcp_server`、`user_model` 等
- **写门控**：restore 流程有严格 quiesce/checkpoint 门控，直写 sqlite 有锁库/损坏风险（印证方案判断）

### 2.3 DataApi 是 IPC 内部服务

- `src/main/data/README.md`：DataApi 是 Electron/IPC 特殊 case，依赖 WindowManager
- `src/main/ipc/IpcApiService.ts`：IPC 请求路由，非 HTTP
- **结论**：Agent/Provider/SKILLS/MCP 的增删改查全走 IPC（renderer ↔ main），Sidecar 无法经 HTTP 调用

### 2.4 bundled MinGit（影响 6B.1）

`src/main/utils/bundledGit.ts`：
- Windows 下自带 MinGit，路径 `resources/binaries/<platform>/git/cmd/git.exe`
- `getBundledGitDir()` 把 MinGit 追加到 PATH 尾部
- **结论**：CherryStudio 智能体即使系统没装 Git Bash，git 命令也能用（bundled MinGit 兜底）

### 2.5 删除按钮（锁死注入点）

- Agent 删除：`Sessions.tsx` `canDelete={!!workspaceId}`，`DELETE /agents/:agentId`（DataApi）
- Provider 删除：`useProviderDelete.ts` → `deleteProviderById`（DataApi）
- **结论**：无受管标记，需注入器在 renderer 层加 `managed` 判断

### 2.6 更新机制

- `AppUpdaterService.ts`：electron-updater，`autoUpdater.channel` 可配
- `electron-builder.yml`：`publish: { provider: generic, url: https://releases.cherry-ai.com }`
- **结论**：可接管 feedURL 指向自有更新通道

## 三、方案 v3.1 偏差清单（必须修正）

### 🔴 偏差 1：Sidecar 派发 Agent 的通道假设不成立

**方案 v3.1 假设**：Sidecar 经官方 API `/v1/agents` 建/改/删 Agent（M2 原型实测 188 有该路由）。

**源码事实**：v2.0.1 官方 API Gateway **无 `/v1/agents` 路由**。

**解释**：M2 原型实测的 188 测试机（HOST_188:23333）返回 `/v1/agents` 200/401，说明**该机 CherryStudio 版本与源码 v2.0.1 不一致**（可能是旧版 2.0.0 或带自定义 API 的版本）。官方最新源码已移除/从未有该路由。

**影响**：Sidecar 无法依赖官方 API 派发 Agent。必须改走：
- **路线 A（推荐）**：Fork 源码，在 API Gateway 加 `/v1/admin/agents` 等管理路由（走 ProviderService/AgentService 正常方法，不锁库、可热更新）
- **路线 B**：Sidecar 直写 SQLite（有锁库/损坏风险，方案已否决）
- **路线 C**：Sidecar 经 IPC 调用（不可行，IPC 是 renderer↔main 内部通道）

### 🔴 偏差 2：DataApi 不可被 Sidecar 调用

**方案 v3.1 假设**：Sidecar 可调用 DataApi 管理 Agent/Provider。

**源码事实**：DataApi 是 IPC 内部服务，非 HTTP，Sidecar 无法调用。

**影响**：同偏差 1，必须走 Fork 加管理路由。

### 🟡 偏差 3：Git Bash 依赖需修正

**方案 v3.1 假设**：智能体依赖 Git Bash，缺则不可用。

**源码事实**：自带 bundled MinGit 兜底，git 命令无系统 Git 也能用。

**影响**：6B.1 的"Git Bash 依赖"需弱化——bundled MinGit 已保证 git 可用。但**完整 Git Bash（bash 终端）**仍可能缺失（Agent 是 claude-code 类型，需 bash 环境）。修正为：服务端可见"系统 Git Bash 是否安装"，缺则管理员可远程装完整 Git for Windows（bundled MinGit 只保证 git 命令，不保证 bash 终端）。

## 四、缺失模块（方案 v3.1 未覆盖，需补齐）

| # | 缺失模块 | 说明 |
|---|---------|------|
| 1 | **Fork 管理路由层** | 官方 API 无管理路由，需 Fork 加 `/v1/admin/*`（agents/providers/skills/mcp） |
| 2 | **Fork 构建/发布链路** | 需维护 fork 源码 + 自建 Windows 安装包 + 自有更新通道 |
| 3 | **受管标记数据模型** | agent/user_provider/mcp_server 表无 managed 字段，需加列或旁路表 |
| 4 | **Sidecar 与 Fork 的鉴权** | Sidecar 调 Fork 管理路由需独立鉴权（区别于官方 API key） |
| 5 | **Git Bash 完整版检测** | 需区分 bundled MinGit 与系统完整 Git Bash |
| 6 | **升级自愈的补丁库** | 需按 CherryStudio 版本维护注入器适配（v2.0.0/v2.0.1/未来） |

## 五、校验结论

**方案 v3.1 的架构方向（补丁包 + Sidecar + 服务端 + Web后台）正确，但核心执行通道有致命偏差**：

1. **Sidecar 不能依赖官方 API 派发 Agent/管模型** —— 官方 API 只有 AI 转发类路由，无管理路由
2. **必须 Fork 源码加管理路由** —— 这是唯一不锁库、可热更新的通道
3. **Fork 层从"可选"升级为"必需"** —— 方案 v3.1 把 Fork 层（UI 锁死）和 Sidecar 层并列，但实际 Fork 层还承担"管理路由"职责，是 Sidecar 派发的前提

**修正方向**：最终方案 v4.0 需把 Fork 层提升为核心（加管理路由 + UI 锁死 + 更新接管），Sidecar 层作为"常驻执行器"（连服务端 + 调 Fork 管理路由 + 数据采集 + 自愈）。
